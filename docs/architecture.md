# 架构与审核边界

仓库中的 `stickers/` 与 `redirects.yaml` 表达期望的图库状态。一个 PR 是一次状态变更集合，不能等同于单个 mutation。构建从目标分支快照和候选快照计算全部变更，再校验候选快照的整体一致性。没有在线写入 API 或数据库。

## 处理模型

| 对象 | 负责的约束与行为 |
| --- | --- |
| `Source` / `Metadata` | 来源、图片文字与标签的合法性，文字规范化及来源保留判断 |
| `ImageAsset` | 解码与格式限制、哈希、内容等同判断、原图与缩略图输出 |
| `ProcessingPolicy` / `ImageProcessor` | 声明式裁剪与尺寸约束、保守自动裁边和禁止放大的处理流程 |
| `Sticker` | 稳定 ID 下的图片和描述，计算同一条目的多个变更 |
| `RedirectTable` | 合并后的 ID 解析，拒绝循环及悬空目标 |
| `CatalogSnapshot` | 完整图库读取与静态索引输出 |
| `ChangeSet` / `Mutation` | 两个快照间的全部 mutation，定位变化图片 |
| `DuplicateReview` / `OcrAdvisor` | 传统去重复核证据及 OCR 建议，不决定人工内容审核 |
| `ReviewReport` | 供维护者查看的结构化和文字报告 |
| `BuildDestination` / `CatalogBuilder` | 输出目录边界与完整构建顺序 |

`CatalogCommand` 是命令行边界。前端通过静态 `manifest.json` 读取发布数据，目录搜索、收藏和界面交互由各自的对象负责。源文件校验规则与前端显示需求不共享可变状态。

图片输出区分 `original`（投稿字节不变）、`display`（默认展示和下载）及 `preview`（从展示图生成的缩略图）。处理参数保存在源元数据中，报告通过 `processingReport` 记录实际结果；参数变化产生独立的 `REPROCESS`，可以和同一 PR 中其他 mutation 共存。处理后的资源地址必须包含处理配方版本和参数影响，避免调整尺寸后命中旧缓存。

## 已选择的简化

- 图片相似性采用成熟 pHash 实现，文字比较采用成熟编辑距离实现；精确重复经过字节确认。
- 近似结果只给证据，不用阈值直接删除；同底图配字不同是正常变体。
- 手工录入的文字是发布依据，OCR 只是建议。
- 截图仅自动裁连续的非白色纯色边缘；带图标状态栏采用显式坐标，处理策略不能猜测用户想保留哪一部分。
- 生成物只保存为 CI 产物，不回写源码或贡献者分支。
- 当前完整图库参与检查，首版接受批处理开销；没有为了假设中的规模增加向量服务、任务队列或数据库。

## 三个审核视角

架构审核按以下问题检查实际代码，已执行的分判、证据与整改结果见审核记录。本文说明设计，线上部署与站点验收另行核实。

- **Evans**：条目、来源、合并和 mutation 是否表达真实领域；一个 PR 多操作以及合并来源是否保持一致。
- **Ousterhout**：图片解码、YAML 验证和输出资源等复杂细节是否封装在稳定接口后，调用者是否被迫了解内部流程。
- **Kay**：对象是否拥有自身约束与行为，是否通过明确方法合作，避免以全局字典和过程链冒充 OOP。

实际审计见[三巨头审核记录](architecture-review.md)，记录代码结论与上线证据的区别。
