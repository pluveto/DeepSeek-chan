**分判：Evans、Ousterhout、Kay 均为有条件通过；不能据此宣称最终审核通过或部署完成。**

| 条件 | 证据与必须修复的行为 |
| --- | --- |
| 合并保留所有参与条目的出处 | `ChangeSet` 当时只校验 donor 来源，survivor 原出处可被删除；已用实际条目复现。需要强制保留合并参与者的来源并集。 |
| 快照的公开构造入口保证有效性 | `CatalogSnapshot` 当时可接受无效 ID 与任意对象，与完整有效快照的接口约定矛盾。需要集中维护类型、身份、条目数量和总大小约束。 |
| 报告封装自身状态 | `CatalogBuilder` 当时直接修改 `ReviewReport.data` 并返回共享字典。需要消息接口和独立导出，避免调用方依赖内部表示。 |

首轮已有 Python 和前端模型测试通过的本地证据，但这不覆盖后续变更，也不代替 CI、部署和浏览器验收。

## 三个人的讨论

- Evans 要求保留来源并集，Ousterhout 用真实条目复现旧代码的 survivor 来源丢失，认为其优先级高于形式上的类组织问题；修复后双方确认多 donor 与重定向链都应检查最终保留条目。

- Ousterhout 与 Evans 同意原图身份必须稳定，派生地址应随处理策略和配方改变；不为静态 CPU 流程新增实体数据库或持久化框架。

## 容量与 OCR 复审：2026-10-01

审核对象：提交 `f1d3a0e`，PR #2 的容量与 OCR 变更；不包含工作区新采集的投稿。本轮三位审核员独立取证并交叉讨论，作者未担任自审。

### Eric Evans

**分判：通过。** 原图总量上限仍由 `CatalogSnapshot.MAX_TOTAL_BYTES` 统一约束，读取和公开构造入口均执行限制；提高到 1 GiB 没有撤销单图大小、像素和动画限制。OCR 仍是建议，不覆盖人工文字。独立运行 63 项 Python 测试通过。1 GiB 是原文件准入上限，不能理解为整个进程的内存上限。

### John Ousterhout

**分判：通过。** `OcrAdvisor.suggest(snapshot, changes)` 的调用协议未扩大，线程池、每图临时目录、Tesseract 环境和超时处理封装在模块内部；调用方不必承担并发调度。排序后映射保证输出顺序稳定，两个 worker 限制并发，单独环境字典避免修改进程全局环境。独立运行 63 项 Python 测试通过；三项新增测试覆盖并发峰值、独立目录与清理、环境隔离、逐图失败、变更筛选和工具缺失。没有把修改常量或通过单元测试当作大容量压测完成。

### Alan Kay

**分判：通过。** 并发工作读取不可变快照，每个任务拥有自己的临时目录和进程环境；结果通过返回值汇总，工作线程不共享可变建议字典。OCR 建议消息与人工文字的状态归属仍分离。独立运行 63 项 Python 测试通过。采集中的新投稿不属于本次基础设施提交的审核范围。

### 三个人的讨论

- Ousterhout 向 Evans 和 Kay 质疑部署文档“适配数百张”是否会被理解为吞吐保证。三人确认 40 分钟只是 CI job 的硬上限：500 张若每张都耗尽 30 秒，两个 worker 单计 OCR 即需约 125 分钟，因此不能保证任意数百张都在限时内完成。整体超时会使检查失败，依赖检查成功的发布不会继续。
- Evans 和 Kay 认为不能由最坏全超时假设直接要求把预算提升到 125 分钟；Ousterhout 同意。应把正常批量目标与最坏完成承诺分开，并建议部署说明直写硬上限及超时后果。
- 三人确认 1 GiB 仅约束原图字节总量；before/after 快照、派生图片及解码会增加内存占用。当前没有最大容量的内存压测证据，真实批次应由实际 CI 结果验收。

### 最终意见

**总判：通过本次代码与协议审核，可在 PR 检查成功后合并。** 未发现需要阻断合并的 OOP 或并发封装缺陷。该结论不保证 1 GiB 图库在所有运行环境中完成，也不表示数百张 OCR 的最坏耗时已通过验证。

后续验收：真实大批次执行时记录总耗时、内存及 OCR 失败结果；只有取得该证据后才能声称相应批次容量和吞吐已验证。当前无需仅为最坏假设扩大 CI 时间预算或新增调度框架。
